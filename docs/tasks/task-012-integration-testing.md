# Task 012: 핵심 기능 통합 테스트

## 개요

- **목표**: Task 007~011에서 개별적으로 구현/검증된 주최자·참여자·관리자 플로우를 하나의 시나리오로 이어서 검증하고, 개별 Task 테스트에서 다루지 않은 경계(플로우 간 전환, 에러/엣지 케이스)를 확인한다
- **예상 소요 시간**: 반나절
- **관련 기능**: F001~F015 전체 (신규 구현 없음, 검증 전용 Task)
- **의존성**: Task 007~011 전부

## 배경 / 현재 상태 및 제약

- 지금까지 Task 008~011에서 각 기능은 이미 개별적으로 Playwright/Claude in Chrome으로 검증됨. Task 012는 새 코드를 추가하는 Task가 아니라, **여러 Task의 결과물을 하나의 사용자 여정으로 이었을 때도 깨지지 않는지** 확인하는 회귀·통합 테스트다
- **핵심 제약**: 이 환경의 실제 가입 계정은 2개(`정석`, `이름 없음`)뿐이고 둘 다 `role: user`다. 서로 다른 두 실제 Google 계정으로 "A가 만든 이벤트에 B가 참여" 시나리오를 완전 자동화할 수 없고, admin 로그인도 실제 OAuth 완주가 불가능하다 (Task 008/010/011에서 반복 확인된 동일 제약)
- 따라서 이번에도 기존 패턴을 따른다: **SQL로 역할 승격(admin) 및 참여자 row 보간**을 사용해 "다른 사용자가 이미 참여한/만든" 상태를 만들고, 그 상태에서 실계정(정석) 세션으로 실제 UI 클릭 흐름을 검증한다. 처음부터 끝까지 완전 자동 로그인이 필요한 구간(비로그인 → OAuth 동의 화면 → 콜백)은 리다이렉트 발생까지만 확인한다 — 이는 Task 008/009/010에서 이미 채택된 검증 수준과 동일하다
- `app/error.tsx`, `app/not-found.tsx` 같은 전역 에러 바운더리/404 페이지가 아직 없음(Task 013 범위) — 이번 Task에서 만들지 않고, 현재 Next.js 기본 에러 화면으로 어떻게 보이는지만 확인해 Task 013에 참고 자료로 남긴다

## 구현 사항 (테스트 시나리오 준비 — 코드 변경 없음)

- [ ] 테스트용 이벤트 데이터 생성/정리 스크립트 없이 매 시나리오 SQL로 즉석 생성 후 테스트 종료 시 정리
- [ ] admin 역할 임시 승격/원복은 Task 010/011과 동일하게 SQL로 처리
- [ ] 브라우저 세션은 Claude in Chrome 사용 (Task 009~011과 동일 도구, 일관성 유지)

## 수락 기준

- 주최자 플로우: 로그인 → 이벤트 생성 → 상세 페이지에서 호스트 자동 참여 확인 → 초대 링크 복사 → 수정 → 삭제까지 한 세션 안에서 끊기지 않고 이어진다
- 참여자 플로우: 초대 링크로 이벤트 미리보기 접근 → (이미 참여 중인 상태 포함) 참여 확인 → 상세 페이지에서 참여자 목록에 반영 → `/events`의 "내가 참여한 이벤트" 탭에 노출
- 관리자 플로우: admin 로그인 → 대시보드 지표 확인 → 이벤트/사용자 관리 테이블 이동 → 통계 페이지에서 기간 변경까지 사이드바 네비게이션으로 끊기지 않고 이어진다
- 에러/엣지 케이스: 존재하지 않는 이벤트 ID, 존재하지 않는 초대 코드, 권한 없는 사용자의 이벤트 수정 페이지 직접 접근, 비로그인 사용자의 보호된 페이지 접근이 각각 적절히 처리된다(404 또는 리다이렉트, 크래시 없음)
- 위 세 플로우를 순서대로 실행하는 동안 콘솔 에러가 발생하지 않는다

## 테스트 체크리스트 (Claude in Chrome)

- [x] **주최자 플로우**: 이벤트 생성(제목/날짜/장소) → 상세 페이지 참여자 1명(호스트) 확인 → 초대 링크 복사 버튼 동작("초대 링크가 복사되었어요" 토스트) 확인 → 수정 페이지 이동 후 제목 변경 저장("(수정됨)" 반영, 상세로 정상 복귀) → `/events` "내가 만든 이벤트" 탭에 반영 확인
- [x] **참여자 플로우**: 만든 이벤트의 초대 코드로 SQL 참여자 row를 보간해 "2명 참여 중" 상태 재현 → `/join/[invite_code]` 미리보기에서 정확히 반영됨 확인 → 이미 host로 참여 중인 계정이 "참여하기" 재클릭 시 에러 없이 정상 이동 + 참여자 수 유지(중복 방지 회귀 확인)
- [x] **관리자 플로우**: SQL로 admin 임시 승격 → `/admin/dashboard` 지표 확인 → 사이드바로 이벤트 관리 → 사용자 관리 → 통계 분석 순서로 이동, 페이지 전환 간 콘솔 에러 없음 확인 → 통계 페이지 기간 드롭다운을 7일→90일로 변경해 실시간 재조회 확인 → 완료 후 SQL로 role 원복, 원복 후 접근 거부(`/admin/login?error=forbidden`) 회귀 확인
- [x] **에러 케이스**: `/events/00000000-0000-0000-0000-000000000000`(존재하지 않는 UUID) → 404, 콘솔 에러 없음. `/join/NOTREAL1`(존재하지 않는 초대 코드) → 404, 콘솔 에러 없음
- [x] **엣지 케이스(신규 발견)**: 권한 없는 사용자가 남의 이벤트 수정 페이지(`/events/[id]/edit`)에 직접 URL 접근 → **최초 시도에서 결함 발견**: 소유권 검증 없이 폼이 그대로 노출되고, 제출 시 PostgREST 원시 에러 메시지가 사용자에게 노출됨. 즉시 수정 후 재검증: 소유자가 아니면 404, 본인 이벤트는 정상 노출·저장되는 회귀 없음 확인
- [x] **콘솔 에러 점검**: 세 플로우 전체 진행 동안 매 페이지 전환마다 `read_console_messages`로 확인, 발견된 두 결함(아래 참고) 외에는 에러 없음

## 발견 및 수정한 결함

통합 시나리오 중 "권한 없는 사용자가 남의 이벤트 수정 페이지에 직접 URL 접근"하는 경로를 처음으로 테스트하다 발견. 개별 Task(009)에서는 서버 액션의 소유권 검증만 확인했고, 페이지 레벨 UI 가드는 검증 대상이 아니었어서 지금까지 드러나지 않았다.

1. **UI 소유권 가드 누락**: `/events/[id]/edit` 페이지가 `created_by` 체크 없이 `getEventById`만 호출 — 로그인만 되어 있으면 누구나 URL로 남의 이벤트 수정 폼(제목/장소/날짜 등)을 볼 수 있었음. 상세 페이지(`/events/[id]`)는 `isHost` 조건부 렌더링으로 이미 막고 있었으나 수정 페이지에는 동일한 가드가 없었음. `event.created_by !== userId`일 때 `notFound()`(403이 아닌 404 — 존재 여부 자체를 노출하지 않기 위함)로 수정
2. **원시 DB 에러 메시지 노출**: 위 상태에서 실제 저장을 시도하면 서버 액션(`updateEvent`)의 `.eq("created_by", userId)`가 정확히 차단하지만, 매치 실패 시 발생하는 PostgREST 에러(`PGRST116: Cannot coerce the result to a single JSON object`)를 `error?.message ?? "..."` 패턴으로 그대로 사용자에게 노출하고 있었음. `createEvent`/`updateEvent`/`deleteEvent`(`lib/actions/events.ts`) 및 `updateProfile`(`lib/actions/profile.ts`) 네 곳 모두 동일 패턴이라 함께 고정 문구로 교체
